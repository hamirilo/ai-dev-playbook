# 品質確認プレイブック

性能、アクセシビリティ、レスポンシブ対応、実ブラウザ上の操作性を、実装後に確認するための手順です。全画面に同じ確認を要求するものではなく、画面の重要度と変更範囲に応じて使います。

このPlaybookでは、必須ゲートと品質推奨を分けて扱います。対象プロジェクトで定義されている型チェック、Linter、Build、基本テストは必須ゲートです。Lighthouse、Core Web Vitals、N+1クエリ対策、高度なパフォーマンス最適化はSoft Targetです。

AIエージェントは品質推奨を常時適用せず、ユーザーから明示的な指示がある場合、または大規模なUI・パフォーマンス変更を行う場合に参照・適用します。

## 使う場面

- 新しい主要画面や導線を追加したとき
- 一覧、検索、フォーム、React Islandを大きく変更したとき
- JavaScript、CSS、画像、フォント、外部スクリプトを追加・変更したとき
- 共通UIコンポーネントを変更したとき
- レイアウト崩れ、遅い操作、キーボード操作の問題が報告されたとき
- リリース前に代表的な画面を確認するとき

## 手順

### 1. 代表ページと完了条件を決める

最低限、変更の影響を受けるページを1つ以上選びます。規模が大きい場合は、トップ、一覧・検索、フォーム、詳細から代表ページを選びます。

次を作業開始時に決めます。

- どの利用者・端末幅を対象にするか
- 主要操作を何とするか
- Lighthouseやブラウザで何を確認するか
- 今回は確認しない範囲と、その理由

### 2. 生成物を使って測定する

開発サーバーだけでなく、本番に近いビルドと設定で確認します。

- 最適化済みのCSS、JavaScript、画像を使う
- ステージングなど、本番に近いサーバー性能で確認する
- 認証画面はテスト用アカウントで確認し、認証情報をログへ出さない
- 同じページを同じ条件で複数回測定し、極端な一回の結果だけで判断しない

### 3. Lighthouseを実行する

代表ページについて、次を確認します。

- Performance
- Accessibility
- Best Practices
- SEO（外部公開や検索流入が必要な場合のみ）

Performance、Accessibility、Best Practicesは100を目標にします。ただし100点そのものを機械的な合格条件にせず、少なくとも90未満の項目、重大なアクセシビリティ問題、利用者の主要操作を妨げる問題を優先して直します。

スコアを上げるために機能や意味のあるアクセシビリティ情報を削らないでください。未達を残す場合は、未達項目、理由、利用者への影響、再確認の条件を報告します。

### 4. Core Web Vitalsを確認する

目安として次を確認します。

| 指標 | 良好な目安 |
|---|---:|
| LCP | 2.5秒以内 |
| INP | 200ミリ秒以内 |
| CLS | 0.1以下 |

ラボ計測は回帰確認に使います。可能であれば実利用環境のデータも確認し、初期表示だけでなく、操作後の遅延やレイアウトシフトも見ます。

### 5. 実装品質を確認する

### N+1クエリ

一覧・検索・詳細画面で、表示件数や関連データの増加に比例してクエリ数が増えないか確認します。

- ForeignKeyやOneToOneは、必要に応じてselect_relatedを使う
- 多対多や逆参照は、必要に応じてprefetch_relatedを使う
- 取得した関連をテンプレート、Serializer、Presenterなどで再度遅延取得していないか確認する
- ページング後の件数だけでなく、関連データの取得クエリも確認する
- 重要な一覧・検索では、クエリ数を固定するテストや計測を検討する

すべてを先回りして取得すればよいわけではありません。画面が必要とするデータと計測結果に基づいて、取得範囲を決めます。

### TypeScriptと型検査

Reactの共有実装はTypeScriptを基本とし、コンポーネントはTSX、ロジックはTSで記述します。

- JSXを追加する前に、TSXへする必要がないか確認する
- typecheckを実行し、暗黙のanyや不整合なPropsを残さない
- anyでエラーを隠さず、unknownや適切な型、型ガードを検討する
- APIレスポンス、Djangoから渡るJSON、localStorageなど外部境界は実行時検証を検討する
- TypeScriptの型検査は実行時検証やサーバー側バリデーションの代替にしない

### 機械的な検証（必須ゲートを含む）

プロジェクトで用意されている次の検証を、意味の判断より先に実行します。型チェック、Linter、Build、基本テストは対象となる場合に必須ゲートとして扱います。

- formatter
- lint
- typecheck
- 単体テスト・結合テスト
- Storybook build
- 依存関係やバンドルサイズの確認

## 6. 実ブラウザで主要操作を確認する

自動テストやスコアに加えて、次を手動またはブラウザ自動化で確認します。

- キーボードだけで主要操作を完了できる
- フォーカスが見え、ダイアログ・メニューを閉じた後の戻り先が自然である
- 読み込み中、空、エラー、成功、大量データの状態が成立する
- 長い文字列やサーバー側バリデーションエラーで崩れない
- モバイル幅・狭い画面幅で操作が隠れない
- 連打、二重送信、戻る操作、再読み込みで状態が壊れない
- コンソールエラー、不要なネットワーク失敗、レイアウトシフトがない
- reduced motionの設定を尊重できる

## 7. 結果を報告する

PRや完了報告には、必要に応じて次を含めます。

- 対象ページ、利用者、端末幅、測定環境
- Lighthouseの各カテゴリ結果
- Core Web Vitalsの結果
- 実施した主要操作と結果
- 未確認事項、未達項目、残るリスク
- 再確認が必要になる条件
