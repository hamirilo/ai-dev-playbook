# 安全な実装とエラー処理

この文書は、[Architecture Standard](https://github.com/jazmf-dx/ai-dev-standards/blob/main/standards/architecture/README.md) の安全性に関する原則を、実装時に確認するための手順です。

## 変更前に境界を確認する

- 誰が操作できるか
- どのデータを読み書きするか
- 外部サービスを呼ぶか
- 失敗しても再実行できるか
- ログに何を残し、何を残してはいけないか
- 失敗時に利用者が取れる次の行動は何か

## 認証・認可

- 認証済みかどうかだけでなく、対象リソースへの業務権限を確認する
- 画面、API、非同期処理で認可ロジックを分散させない
- リソースの存在を隠す必要がある場合は404を返す
- 権限エラーをフロントエンドの表示制御だけで防がない
- ログイン状態やトークンを独自の仕組みで重複管理しない

## CSRFとブラウザ境界

- DjangoのCSRF保護を無効化しない
- Reactから状態変更する場合も、サーバーが発行したCSRFトークンを正しく送る
- Django TemplateからReactへ値を渡すとき、ユーザー入力をHTML属性へ文字列連結しない
- JSONは安全なシリアライズ手段で埋め込み、HTML・JavaScriptの文脈を混同しない
- CORSを広く許可して問題を回避しない

## 外部通信

外部HTTP通信を追加・変更するときは、次を実装前に決めます。

- 接続と応答のtimeout
- リトライするエラーと、リトライしないエラー
- 同じ要求を複数回送っても安全か
- 証明書検証を維持できるか
- 外部障害時の画面表示とログ
- 後から再実行する手段

`timeout`なしの通信、証明書検証の無効化、例外の握り潰しを行いません。

## エラーの分離

### 入力・業務エラー

利用者が修正できるエラーは、入力欄やフォームの近くに理由と修正方法を表示します。

### 外部サービスエラー

利用者に「もう一度試す」「後で再実行する」などの回復手段を示し、運用者にはサービス名・操作・結果・request IDを記録します。

### 想定外エラー

内部の詳細やstack traceを画面へ表示せず、調査に必要な情報を構造化ログへ残します。`except Exception: pass` のように成功したように見せません。

## UIフィードバック

UIの表現はApplication UI Standardに従い、意味を重複させません。

| 状況 | 基本の表現 |
|---|---|
| 入力項目の不備 | Field Error |
| フォーム全体・業務エラー | Form Error / Alert |
| 保存や非同期処理の結果 | Toast |
| 機能全体が利用不能 | Error State / Error Page |

エラーをToastだけに表示したり、サーバーの例外文をそのまま画面へ出したりしません。

## ログと監査記録

障害調査に必要なログには、可能な範囲で次を含めます。

- timestamp
- level
- service / environment
- message
- request_id
- user_id（必要な場合だけ）
- action / resource / outcome（業務イベントとして必要な場合）

Password、Token、Secret、個人情報、認証ヘッダー、外部URLの秘密部分をログへ出しません。

監査記録はすべての処理を無条件に残すのではなく、認証失敗、権限変更、破壊的操作、一括処理、重要データ変更など、後から説明が必要なイベントを優先します。

## 実装後のチェック

- 認証なし・権限なし・対象外リソースを確認した
- CSRF、入力値、HTML属性、JSON境界を確認した
- 外部通信にtimeoutと失敗時の扱いがある
- 例外を握り潰していない
- 利用者向けメッセージと内部ログを分離した
- ログにrequest IDがあり、秘密情報がない
- 失敗後の再試行・再実行方法が分かる
