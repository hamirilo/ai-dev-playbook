# テスト・レビュー・UI確認プレイブック

テストが通っただけでは、利用者にとって正しいとは限りません。壊れた場合の影響が大きい境界から検証します。

## 検証の順序

1. Formatter / Linter / Type Checkerなど機械的な検査
2. 変更したロジックの自動テスト
3. 既存の関連テスト
4. API・外部連携・データ境界のテスト
5. ブラウザでの主要操作確認
6. 差分とログを人間が確認

プロジェクト固有のコマンドを使い、コマンド名をPlaybookへ固定しません。

## 優先してテストするもの

- ビジネスルールと状態遷移
- 認証・認可の境界
- DB制約と重要な入力制約
- 外部サービスの成功・失敗・タイムアウト
- データ更新の冪等性と二重送信
- 重要な画面の読み込み中・空・失敗・大量データの状態

単純なフレームワークの挙動を大量に再テストするより、プロジェクト固有の壊れ方を優先します。

## 認可のテスト観点

最低限、次の利用者を分けて確認します。

| 利用者 | 確認すること |
|---|---|
| 未認証 | ログイン導線または拒否が正しいか |
| 一般ユーザー | 自分の操作だけ許可されるか |
| 権限保持者 | 担当する機能を操作できるか |
| 対象外ユーザー | URLを直接指定しても越権できないか |

存在を隠す必要があるリソースは404、単なる権限不足は403を期待値として確認します。

## レビューの8観点

### 1. エラーパス

外部通信、メール、ファイル処理、保存失敗が起きたときに、握り潰さず利用者と運用者へ伝わるか。

### 2. 並行実行

同時更新、連打、再送、定期処理の重複実行でデータが壊れないか。

### 3. データライフサイクル

削除、無効化、所有者変更、参照先の消失が、画面・履歴・集計に与える影響を確認したか。

### 4. 外部制約

認証期限、レート制限、タイムアウト、証明書、外部サービス停止を考慮したか。

### 5. UXギャップ

処理中、部分失敗、空状態、再試行方法が利用者に分かるか。

### 6. 運用・スケール

ログ、一覧、検索、エクスポート、バックグラウンド処理がデータ増加後も調査可能か。

### 7. データ整合性

Model、DB制約、入力、状態遷移の間に抜けや矛盾がないか。

### 8. 認証・認可境界

すべての入口（画面、API、直接URL、非同期処理）で同じ認可判断が適用されるか。

## UIの実動確認

自動テストに加えて、主要操作をブラウザで確認します。

- 初期表示とレイアウトシフト
- キーボード操作とフォーカス
- 読み込み中、空、エラー、成功
- モーダルの開閉、キャンセル、二重送信
- サーバー側バリデーションエラーの再表示
- 画面幅を変えたときの崩れ
- セマンティックTokenから外れた直接色指定がないか

## レビュー報告の形式

指摘ごとに次を短く書きます。

```text
重大度: Critical / Major / Minor
場所: file:line
問題: 何が起きるか
影響: どの利用者・データ・運用に影響するか
対処: 何を変更するか
検証: どう確認するか
```

問題がない観点を長く説明する必要はありません。未確認の観点だけを明示します。
