# AI支援開発の進め方

機能追加、バグ修正、リファクタリングをAIエージェントと進めるときの実行手順です。
全体の判断原則は [AI Development Standards](https://github.com/hamirilo/ai-dev-standards) を先に確認します。

## 使う場面

- 変更範囲が複数ファイルにまたがるとき
- 既存実装の調査が必要なとき
- 動作確認やレビュー観点を毎回考え直しているとき

単純な1ファイル修正では、必要な手順だけを使います。

## 基本ループ

### 1. 目的と完了条件を固定する

最初に次を短く書きます。

- 何を変えるか
- 何を変えないか
- 利用者から見た完了条件
- 影響を受ける境界（認証、データ、外部サービス、UI）
- 実行する検証

完了条件が曖昧なまま実装を始めないでください。後からAIが推測した仕様を修正する方が高くつきます。

### 2. 必要なコンテキストだけを調べる

次の順で対象を絞ります。

1. プロジェクトの入口、コンテキスト、関連ADRを読む
2. `ai-dev-standards` のCore Standardを読む
3. タスクに関係するPlaybookだけを読む
4. 対象ファイル、呼び出し元、類似実装、関連テストを検索する
5. 変更しない範囲を確認する

リポジトリ全体を最初から読み込んだり、無関係な履歴を大量に渡したりしません。検索結果はファイル名と該当箇所を中心に要約します。

### 3. 設計を小さく決める

実装前に、少なくとも次を確定します。

- 既存実装を使えるか
- 新しいレイヤーや依存が本当に必要か
- データの所有者と更新経路
- 失敗時の表示・記録・再実行方法
- テストで確認する振る舞い

全体の構成を作り直すのではなく、目的を満たす最小の変更にします。

### 4. 小さい単位で実装する

- 1ステップごとに実行可能な状態を保つ
- 無関係な整形・改名・移動を混ぜない
- 既存のコンポーネント、関数、テストを優先して使う
- 仕様変更とリファクタリングを同じ変更に混ぜない
- 自動生成されたコードやフォーマット結果を手作業で再調整しない

### 5. 機械的な検証を先に実行する

プロジェクトで用意されたFormatter、Linter、Type Checker、テストを実行します。
機械的に判定できる問題を、AIの推論や人間の目視だけで確認しないでください。

自動修正できるものはツールで直し、意味の判断が必要な問題だけをAIまたは人間が確認します。

### 6. 壊れるシナリオをレビューする

最低限、次を確認します。

- 正常系だけでなく入力エラー・権限エラー・外部障害が扱われるか
- 同時更新や二重送信でデータが壊れないか
- 削除・状態変更の影響範囲が把握できるか
- ログに調査に必要な情報があり、秘密情報が出ていないか
- 空・読み込み中・失敗・大量データのUIが成立するか
- 変更した契約を既存の利用側が壊さないか

### 7. 人間へ引き渡す

完了報告には次を含めます。

- 変更したファイルと目的
- 実行した検証と結果
- 影響範囲と未確認事項
- 仕様上の判断、残るリスク、次の作業

AIが勝手に仕様を確定したように見える報告や、「テストが通った」だけの報告で終わらせません。

## コストを抑える原則

- Standardは毎回全量ではなく、タスクの入口として必要な部分だけ読む
- 調査は検索語・対象ディレクトリ・目的を先に決める
- 同じ失敗を繰り返す場合だけPlaybookへ昇格する
- FormatterやLinterの結果をAIに長文で説明させず、エラー箇所を修正させる
- 1回の依頼に実装、全面リファクタリング、設計刷新を同時に含めない

## よくある失敗

| 失敗 | 改善 |
|---|---|
| 最初に全ドキュメントを読ませる | 入口からタスクに必要な文書だけ読む |
| 既存実装を探さず新しい抽象化を作る | 類似コードと利用実績を先に検索する |
| テスト成功だけで完了とする | UI、権限、失敗、データ境界も確認する |
| フォーマットをAIに手作業で合わせさせる | Formatterを正とし、自動修正する |
| 一度の変更で多くのファイルを整理する | 目的ごとに変更を分ける |
