# API実装プレイブック

APIは、画面を作るたびに追加するものではありません。まずDjango Template / Form / 部分HTMLで完結できるかを確認し、それでも明確な境界が必要な場合に実装します。

## APIを検討する場面

- 外部システムや別クライアントとの連携
- 複雑な非同期データ取得
- モバイルや別アプリなど、HTMLを直接利用しないクライアント
- UIとサーバーのデータ境界を明確にする必要がある処理

React Islandを使うことだけを理由にAPIを増やしません。

## 実装前の設計

### 入出力

- 入力Schemaと出力Schemaを分ける
- Django Modelをそのまま返さない
- 公開してよいフィールドだけを明示する
- null、空文字、日時、金額、IDの表現を決める
- 一覧はページング、並び順、フィルター条件を決める

### 認証・認可

- APIごとに認証方式を明記する
- 認証と業務認可を分ける
- 画面側でボタンを隠すだけで認可を済ませない
- 他人のリソースを返す場合の404 / 403の方針を決める

### エラー

少なくとも次を区別します。

- 入力不備
- 認証・認可エラー
- 対象リソースなし
- 競合・状態不正
- 外部サービス障害
- 想定外エラー

クライアントが処理できる安定したエラー形式と、利用者向けの安全なメッセージを用意します。

## Django Ninjaでの実装例

```python
from ninja import Router, Schema

router = Router()


class RecordOut(Schema):
    id: str
    title: str
    state: str


@router.get("/{record_id}", response=RecordOut)
def get_record(request, record_id: str):
    record = get_object_or_404(
        Record,
        id=record_id,
        owner=request.user,
    )
    return record
```

実際の認証、認可、Schema、エラー形式はプロジェクトのStandardと既存API契約に合わせます。

## 互換性

- 既存クライアントが使うフィールドを削除・改名・型変更しない
- 追加は後方互換性を確認して行う
- 破壊的変更は新しい契約または同時更新の計画を用意する
- エラー形式も契約として扱う
- 外部公開する場合は認証、レート制限、監視、ドキュメントの責任者を決める

## 外部連携・非同期処理

- 外部HTTP通信にはtimeoutを設定する
- リトライは冪等性とセットで考える
- 失敗時に処理状態を追跡できるようにする
- 大量処理や定期同期は、同期リクエストの中で完了させようとしない
- 部分成功が起きる場合は成功件数・失敗件数・再実行方法を残す

## テスト

- 認証なし、権限なし、対象外リソース
- 入力Schemaの境界値と不正値
- 正常系、重複送信、競合、状態不正
- 外部サービスのtimeout・エラー・再試行
- レスポンスの必須フィールドとエラー形式
- 既存クライアントとの互換性

## APIを作らない方がよい例

- Django Formの送信結果を表示するだけ
- サーバーでHTMLを返せる一覧の検索・ページング
- 既存Viewで十分な処理を、Reactから呼ぶためだけにJSON化する
- 単一画面だけが利用し、将来の利用者も決まっていない内部関数
